Daily job scan. Run every step yourself, unattended. Keep job titles and company names as posted.

## 1. Inputs (all in one Google Sheet)
Spreadsheet id {{SPREADSHEET_ID}}. Use the Google Sheets connector (get_values, append_values). Quote tab names that contain dots or spaces.
- People: tab 'kisiler', columns A:J = isim, email, aktif, admin, cv_kaynagi, profil, hedef_roller, haric_tutulanlar, ozel_kurallar, not. Scan for every row where aktif is "evet". For each person use profil (background), hedef_roller (good fits), haric_tutulanlar (exclusions) and ozel_kurallar (extra rules, follow them exactly). If cv_kaynagi names a Drive folder or file ("drive klasör: <id>" / "drive dosya: <id>" or a Drive link), read those CVs with the Google Drive connector every run; they may change. "-" means use profil only.
- Company list: tab 'good_companies_with_careers.csv', columns A:D = company name, career page, not (note), ilan kaynağı (job source, "type: url", several separated by " | "). It is edited often: read it fresh, include every row with a company name, treat B to D as optional. Skip rows whose note says it duplicates another row.
- Pre-fetched postings: tabs 'ats_kapsam' (tarih, şirket, kaynak, url, durum, toplam ilan, israil ilanı, hata) and 'ham_ilanlar' (tarih, şirket, pozisyon, lokasyon, link, kaynak). An Apps Script fills them every day before this run straight from public ATS APIs (greenhouse, lever, ashby, workable, breezy, workday, amazon). They may be missing or not from today.
- Postings log: tab 'ilanlar', columns A:I = tarih, şirket, pozisyon, link, kimin için, lokasyon, hangi CV, neden uygun, link durumu. Read all of it before scanning; it is the record of everything already reported.

## 2. Collect open postings per company
A company is "covered" when 'ats_kapsam' has rows dated today for it, every one of them has durum "ok", and every source listed in its column D is one of greenhouse/lever/ashby/workable/breezy/workday/amazon (or D is empty and the row in 'ats_kapsam' came from its column B).
- Covered companies: use only their 'ham_ilanlar' rows dated today. These come from live ATS listings fetched today, so their links count as verified; do not browse these companies. Exception: rows with kaynak "workday" whose lokasyon does not name an Israeli place (e.g. "2 Locations") must be confirmed as Israel-based (WebFetch the link or WebSearch the title); drop them if you cannot confirm.
- Every other company (including companies with some 'ok' rows plus a comeet or other source): also use their 'ham_ilanlar' rows from today, then look further, trying these in order and stopping at the first that returns a real list of live postings:
  1. comeet sources: comeet.com board and posting pages are JavaScript templates; fetched, they look the same whether a posting is open or closed, and search engines keep showing closed Comeet postings for months. So first WebFetch the company's OWN careers page (column B, or find it with WebSearch). Many such pages embed Comeet and render server-side; take postings and their links from that live list. WebSearch with allowed_domains ["comeet.com"] may be used only to discover candidate titles; a Comeet posting found only through search is reported only if the company's own careers page lists that same title (then use the link from the careers page). If the careers page cannot be read, report none of that company's Comeet-only postings and add the company to the unreadable list as "<company> (Comeet)".
  2. Otherwise WebFetch the careers page (column B). If column B is empty, find the company's careers page with WebSearch first.
  3. If that is empty or renders nothing: WebSearch "<company> jobs" with allowed_domains ["greenhouse.io","ashbyhq.com","lever.co","workable.com","breezy.hr","comeet.com"]; keep only results that are clearly this company (Comeet results follow rule 1).
  4. Large companies with their own job systems not covered above (Microsoft, Salesforce, Google, Meta, TikTok, Travelers): WebSearch "<company> jobs Tel Aviv" and "<company> jobs Israel" and use results on the company's own careers domain. Do not browse LinkedIn directly and do not use links from aggregator/mirror sites (themuse, builtin, dejobs, glassdoor, indeed etc.).
- If 'ats_kapsam' has no rows dated today (the Apps Script did not run), treat every company as not covered.
Keep only postings located in Israel (Tel Aviv area preferred; hybrid/remote-from-Israel fine). Keep a list of companies where everything failed. A company that was read successfully but has no Israel postings is not "unreadable". A covered company is never unreadable.

## 2b. Link verification (for postings that did not come from 'ham_ilanlar')
Every link you write must be verified live in this run. A link counts as verified if it came from a live listing fetched today (an ATS API or board, or the company's own careers page list), or if you WebFetch the posting URL and it shows this posting's title with a description/apply option. Drop the posting if the page 404s, shows "oops"/error, "no longer available/accepting applications", "position closed/filled", redirects to a generic careers list, or shows a different job. Drop it too if it cannot be verified at all. Strip tracking parameters from links. Count how many candidate matches you dropped as dead/unverifiable.

## 3. Matching
For each active person, match the collected postings against their profil, hedef_roller and haric_tutulanlar (and CVs, if any), and apply their ozel_kurallar. When a person has several CVs, write in "hangi CV" the one that fits best; otherwise follow ozel_kurallar or write the CV's name. Open a posting's full text only when the title alone is not enough to decide, or when a person's ozel_kurallar require it.

A posting is new for a person if its link (or, failing that, company + title) is not already in the 'ilanlar' tab with the same "kimin için" value. Report only new ones.

## 4. Outputs
a) Append every new, verified match to the 'ilanlar' tab in one append_values call on range 'ilanlar'!A:I, one row per posting: tarih (today in {{TIMEZONE}} as text YYYY-MM-DD, prefixed with an apostrophe), şirket, pozisyon, link, kimin için (the person's isim, exactly), lokasyon, hangi CV, neden uygun (one line, Turkish, following that person's ozel_kurallar), link durumu ("açık"). Then re-read the tab to confirm the rows landed.
b) Append exactly one row to the 'tarama' tab with append_values on range 'tarama'!A:B: tarih (today, same format with apostrophe), and a comma-separated list of the companies where everything failed, including "<company> (Comeet)" entries (write "-" if none). Do this every run, even when there are no new postings.
c) The Apps Script emails today's rows (and today's unreadable list) after this run, so rows must be written correctly. Do not create Gmail drafts and never send email.
d) Final response (short, Turkish): number of new rows per person, number of companies covered by the pre-fetched ATS data, number of candidate matches dropped as dead/unverifiable, and the unreadable list.
Never edit or delete existing rows in any tab, and never edit the company list or the 'kisiler' tab.
